# Payment Provider Integration Contract

## Purpose

This document records the safe extension contract for adding payment providers without changing wallet business rules or the existing Flutterwave routes. It is intentionally additive: existing `/api/flutterwave/*`, `/api/paystack/*`, account, authentication, VTU and wallet endpoints remain the compatibility baseline.

## Current repository findings

- Flutterwave has a broad provider route surface for checkout, verification, transfers, bills, virtual accounts and cards.
- Paystack has routes for initialization, account resolution, transfers, verification and webhooks, but `POST /api/paystack/initialize` currently returns HTTP 501.
- Paystack's current `charge.success` webhook validates the signature and stores a duplicate marker, but does not invoke the shared wallet-credit workflow. Do not treat this as production-ready wallet funding.
- Wallet funding is currently coupled to Flutterwave transaction identity and verification enrichment. A provider must not call that workflow until the provider identity and enrichment assumptions have been made provider-neutral and tested.

## Non-breaking integration rules

1. Keep existing provider-specific routes and response shapes working. Add a normalized route only as an additive API; do not repoint old routes in-place.
2. Keep provider secrets exclusively in the backend environment/secret store. Never return secret keys or webhook secrets to the frontend or Firestore documents readable by clients.
3. A provider is not selectable for a capability until its complete lifecycle is implemented: initialize/collect, verify against the provider server, authenticate webhook, reconcile, and atomically fulfill the matching business operation.
4. A webhook must be authenticated using the provider's documented signature scheme and raw request body. Do not persist a processed/idempotency marker before the business operation succeeds or is safely recorded for retry.
5. Use a stable merchant reference generated by this application. Persist provider name, provider transaction ID, merchant reference, amount in minor units, currency, customer/user identity, state, and timestamps.
6. Verify amount, currency, merchant reference, and final provider status server-to-server before wallet credit. Never credit from a browser redirect or unverified webhook body alone.
7. Use one provider-neutral idempotent wallet-credit operation. It must prevent duplicate credits across webhook, client verification, scheduled reconciliation, and manual retry.
8. Keep provider capabilities explicit. Do not infer support for transfers, virtual accounts, bills, refunds, or card operations from support for checkout alone.
9. Keep the current Flutterwave implementation as the default until a replacement provider passes sandbox and production-readiness checks.
10. Use feature flags/configuration to disable a provider immediately without deleting its transaction history.

## Provider readiness matrix

| Provider | Existing support observed | Safe status |
| --- | --- | --- |
| Flutterwave | Existing broad routes and wallet funding integration | Existing path; preserve as-is |
| Paystack | Transfer/account resolution and verification exist; checkout initialization is a stub; webhook does not yet perform wallet credit | Partial; do not enable for wallet funding yet |
| 9 Payment Service Bank (9PSB) | A bank-code mapping exists for 9PSB as a beneficiary bank; no dedicated 9PSB API adapter was found | Not integrated as a provider |
| Clubkonnect | Existing VTU routes are separate from payment collection | Keep separate capability |

## 9PSB onboarding inputs required

Before implementing a 9PSB adapter, obtain the official merchant/fintech API pack from 9PSB. Required inputs:

- Official sandbox and production base URLs.
- Authentication method, token lifecycle, required headers, and key rotation rules.
- Exact request/response schemas for collections/checkout, account resolution, transfers/payouts, virtual accounts, status queries, and refunds (only where contracted).
- Webhook callback specification, signature/hash validation, retry policy, and event identifiers.
- Currency and amount units (major/minor units), reference constraints, expiry rules, and terminal status values.
- IP allowlisting requirements, TLS/certificate requirements, rate limits, and support/escalation contact.
- Sandbox credentials and test cases for success, pending, failed, duplicate callback, timeout, and reconciliation.

A bank code for sending money to a 9PSB account is not evidence of an integration with 9PSB's own payment APIs.

## Acceptance checklist for each provider

- [ ] Credentials absent: provider reports unavailable and cannot be selected.
- [ ] Credentials present: authenticated provider health check succeeds.
- [ ] Checkout initialization validates amount, currency, email/user identity, and unique reference.
- [ ] Verification checks provider status, amount, currency, and reference.
- [ ] Webhook signature is checked against raw bytes.
- [ ] Duplicate and out-of-order events cannot double-credit or downgrade a terminal transaction.
- [ ] Failed/transient operations remain retryable and reconcilable.
- [ ] Wallet credit and ledger update are atomic and idempotent.
- [ ] Existing Flutterwave regression tests and routes still pass.
- [ ] Sandbox end-to-end tests cover all supported capabilities before production enablement.
